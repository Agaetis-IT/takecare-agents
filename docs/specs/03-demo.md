| | |
|---|---|
| Status | Proposed |
| Date | 2026-10-16 |

## Purpose

Show the real product in a meeting, on a laptop, in one command. The demo mode is the product installed with the `demo` values profile, plus a `TakeCareDemo` resource that sets up a scenery (an application, its infrastructure, its documentation) and replayable incidents. **No role contains demo-specific code** (vision, principle 3).

Milestone 1 ships one scenario taken from the challenge POC: **`proxy-timeout`**. Spike 001 builds two more minimal scenarios (`bad-config-rollout`, `missing-secret-key`); they join the product if the spike confirms kagent.

## The `proxy-timeout` scenario

The story the Doc must uncover:

- `billing-api` returns intermittent `504`s; the pod is `Ready`, never restarts, and its memory climbs. Everything points to the obvious (and wrong) reflex: raise the memory limit.
- The real cause is an **invariant between two teams' settings**: the RDS Proxy (ACK `DBProxy`) closes idle client connections after `idleClientTimeout: 600` s, while the application's pool only recycles idle connections after `DB_POOL_IDLE_TIMEOUT_SECONDS=900`. AWS documents the opposite rule. Neither team was wrong on its own; nothing compares the two values.
- The deployment log contains yesterday's infrastructure change on the proxy; a runbook and a past incident make the link findable.

A correct diagnosis names the proxy idle timeout as the root cause and rules out memory.

## Resource

```yaml
apiVersion: takecare.agaetis.fr/v1alpha1
kind: TakeCareDemo
metadata:
  name: demo
  namespace: takecare-demo
spec:
  scenario: proxy-timeout
  appNamespace: demo-apps        # where billing-api runs
  platformNamespace: ack-system  # where the DBProxy lives
  rampMinutes: 4                 # how long the error rate takes to climb
```

### Actions, through annotations

| Annotation (value = any new string, e.g. a timestamp) | Effect |
|---|---|
| `takecare.agaetis.fr/incident` | Resets the scenery, then triggers the failure (applies the DBProxy with 600 s, deploys `billing-api` in `leaky` mode with the 900 s pool) |
| `takecare.agaetis.fr/reset` | Puts the scenery back in a healthy state and deletes the `TakeCareInvestigation`s labelled `takecare.agaetis.fr/alert-namespace=<appNamespace>`, which also clears their cooldown (spec 02: the cooldown state lives in the investigations) |

Annotations make actions declarative, idempotent and visible in `kubectl describe`. The controller records the last handled value in the status so that the same value is not handled twice.

## What the `TakeCareDemo` controller deploys

| Component | Origin in the POC | Notes |
|---|---|---|
| `billing-api` (`facturation-api` in the POC) | `content/app/exporter.py` | Python, built into the `takecare-agents-demo-app` image (no more ConfigMap-mounted code). Modes `healthy` and `leaky`. Exposes `http_requests_total`, `app_heap_bytes`, `db_connection_wait_seconds`. Logs in English. |
| ACK `DBProxy` CRD + resource | `content/ack/` | CRD only, no ACK controller: the resource is documentation the Doc can read |
| Corpus content for the five `demo-corpus` servers | `seed/` + `generate-corpus.py` | **Translated to English** (ADR 0003). Curated seeds carry the scenario signals; generated noise makes the search non-trivial; dates are relative to the incident (regenerated by the controller at each incident), deterministic seed. Written to ConfigMaps read by the servers. |

**Who owns what** (one owner per piece):

| Piece | Owner |
|---|---|
| `TakeCarePlatform`; Prometheus with the demo alerting rules (`HighErrorRate`: 504 ratio > 2 % over 1 m, `for: 30s`; `HighLatencyP99`; `PodNotReady`; `PodCrashLooping`, scoped to the app namespace); Alertmanager routing to `/v1/alerts` with the webhook token; OpenTelemetry Collector; **Jaeger**; ACK `DBProxy` CRD; add-ons `kubernetes`, `prometheus`, `report-slack` (if a Slack token is given) and `demo-corpus` (five servers), with their `TakeCareConnector`s (spec 05) | Chart, `values-demo.yaml` |
| `billing-api`, the `DBProxy` resource, the corpus content | `TakeCareDemo` controller |
| `TakeCareDoc` (level `service`, bound to the demo connectors), `TakeCareDemo` | `make demo-up`, from `demo/manifests/*.yaml` |

Without a Slack token, the demo `TakeCareDoc` has no `report` connector: it is then `Ready=False` (`MissingConnectorType`) by design of spec 02. To keep the demo usable without Slack, the demo profile enables a `report-log` add-on variant of the report server that writes messages to its log and to the investigation status instead of Slack; `make demo-verdict` reads them.

## Make targets

| Target | Behaviour |
|---|---|
| `make demo-up` | Checks prerequisites (Docker with ≥ 4 GB, k3d, kubectl, helm) and says what is missing. Creates the k3d cluster `takecare-demo` (pinned k3s image), installs `takecare-crds` and `takecare` with `values-demo.yaml` (which renders the `TakeCarePlatform` and the connectors), creates the Secrets from environment variables, applies the `TakeCareDoc` (level `service`) and the `TakeCareDemo`, waits until all are `Ready`. Re-runnable: does not reinstall what is in place. |
| `make demo-incident` | Annotates the `TakeCareDemo`; prints the expected alert window. |
| `make demo-verdict` | Waits for the next completed `TakeCareInvestigation` and prints the diagnosis and its usage. Works without Slack. |
| `make demo-screens` | Port-forwards Prometheus (error rate and memory graphs with thresholds), Alertmanager and Jaeger, and prints the URLs. `make demo-screens-stop` stops them. |
| `make demo-bench N=5` | Runs N investigations on the ongoing incident without Slack (spec 04). |
| `make demo-reset` | Annotates the `TakeCareDemo` for a reset. |
| `make demo-down` | Deletes the k3d cluster and local working files. |

Rules carried over from the POC:

- The demo **never changes the user's current kube context**: targets use a kubeconfig written by `k3d kubeconfig write takecare-demo`, passed explicitly.
- Secrets come only from environment variables: `TAKECARE_MODEL_API_KEY` (required), `TAKECARE_SLACK_BOT_TOKEN`, `TAKECARE_SLACK_ONCALL_CHANNEL`, `TAKECARE_SLACK_REVIEW_CHANNEL` (optional). An optional `.env` file is read if present and is listed in `.gitignore`.
- Without Slack, everything still works; diagnoses are read with `make demo-verdict`.

## Status

```yaml
status:
  scenario: proxy-timeout
  phase: IncidentInProgress      # Ready | IncidentInProgress | Resetting | Degraded
  incidentStartedAt: "2026-10-16T02:57:40Z"
  expectedAlertWindow: { from: "2026-10-16T02:59:40Z", to: "2026-10-16T03:01:10Z" }
  lastHandled: { incident: "1760583460", reset: "1760583100" }
  conditions:
    - type: Ready
    - type: SceneryReady         # app, DBProxy, MCP servers, rules in place and up to date
```

`SceneryReady` also detects **drift**, a lesson from the POC (`poc.sh check`): MCP servers serving an outdated corpus or alerting rules that differ from the chart's are reported, not silently ignored.

## Acceptance criteria

1. On a clean Mac (Apple Silicon) and a clean Linux (amd64), `make demo-up` ends with all resources `Ready` in at most 10 minutes, with images pulled from the registry (multi-arch).
2. `make demo-incident` makes `HighErrorRate` fire between 2 and 3.5 minutes later; the pod stays `Ready` with no restart; memory reaches about 70 % of its limit without being OOM-killed.
3. `make demo-verdict` prints a diagnosis that is correct as defined in spec 04 (it names the proxy idle timeout), less than 3 minutes after the alert.
4. `make demo-reset` brings the scenery back to healthy, and a new `make demo-incident` replays the story with a new investigation (cooldown cleared).
5. `make demo-up` run twice in a row changes nothing the second time and ends in less than 1 minute.
6. No target modifies `~/.kube/config` or the current context; no secret is written to a file tracked by Git.
7. Jaeger shows the investigation trace with its `invoke_agent doc` root span.
8. `make demo-down` leaves no k3d cluster, container or port-forward behind.
