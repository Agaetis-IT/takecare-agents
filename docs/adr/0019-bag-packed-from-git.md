# ADR 0019 — An agent's Bag is packed from Git, at configuration time

| | |
|---|---|
| Status | Proposed |
| Date | 2026-11-13 |
| Amends | spec 06 §11 (Base camp), spec 10 §8 |
| Relates to | ADR 0001, ADR 0007, ADR 0008, ADR 0015, spec 06 §5 |

## Context

A Bag is an agent's configuration: its role resource (scope, connectors, level tools, instructions, model, report destination) plus the Map and Topo entries it relies on (spec 06 §11). Roles will also take skills and reusable prompts. These live in Git repositories, which hold every version, the stale and the unreviewed ones included. Something must stand between those repositories and the agents, so that an agent is equipped only with what was approved, at the version that was approved.

The Base camp was first described as the platform plus an agent registry (agentregistry) that would play this part. Assessed on 2026-11-13 at v0.4.0, its latest release, it does not:

- a skill entry is a reference to a Git repository that it pins to a commit, and a prompt is stored inline;
- an entry has no approval state;
- its open-source build accepts every write;
- its chart's default rights include writing workloads and reading secrets, which "Never in your place" forbids us to install.

kagent 0.10.3 takes skills from OCI images, Git references or object storage, and prompts from ConfigMaps; none of its fields reads a registry. So the registry would add an index, not a filter, and the content would still come from Git.

## Decision

1. **Git is where a Bag's resources live and where they are approved.** Role resources, the Map (ADR 0015), skills and prompts are files in the customer's repositories. Approval is a merged pull request. Nothing else is a source of what an agent is equipped with.

2. **The approved list is the filter.** A skill or a prompt an agent may take is named in an approved list kept in the customer's Git: for each name, the repository and the exact commit (or the image digest) that was reviewed. A role resource names what it wants by name. A name that is not in the list, or a reference that is not pinned, equips nothing. The list reaches the cluster as a resource applied by the customer's GitOps; the operator has no Git client and no Git credential (ADR 0001). Its shape is fixed by the spec of the first role that takes a skill.

3. **The operator packs the Bag at configuration time.** When it renders the engine's agent, the operator resolves each name the role resource asks for against the approved list and equips the agent with exactly those pinned references. An agent never asks for a skill or a prompt while it runs, and the model never decides what it is equipped with, as for tools (spec 06 §5). What could not be resolved is left out and reported on the role's status, with the name and the reason.

4. **No agent registry is installed or required.** TakeCare ships none, and the Intendant's inventory is the cluster's (spec 10 §8). The resolution of point 3 sits behind one interface, so that a registry can later become a second source of approved references without changing the roles. That is reconsidered when a registry offers all three of these: an approval state on its entries, an install without rights on the cluster, and an engine that consumes it.

5. **Staleness is a finding, not a silent update.** A newer version in a repository never reaches an agent by itself: it is proposed like any other change, in a status, and a person merges the new pin.

## Consequences

- A customer's Bags are reviewed where the rest of their platform is: in Git, with their own tools and rights. TakeCare adds no database and no write right for this.
- The filter is only as good as the review of the approved list; TakeCare does not judge a skill's content. The Intendant's later levels, which check provenance and the rights a new version asks for, work on that list.
- Fetching a pinned reference at start-up is the engine's work (kagent's skill references). Private repositories need a credential the customer provides, named in the role's connector or platform settings, never generated by the chart.
- The Base camp is the platform and what the customer's Git holds, each piece in its own brick; spec 06 §11 and spec 10 §8 say so.
- Third-party products are watched, the agent registry among them; taking one up is a new ADR.

## Rejected alternatives

- **Install agentregistry as the filter.** It has no approval state to filter on, its catalogue-only use is not documented, its chart's default rights contradict our ground rules, and the engine does not read it.
- **Let the role resource carry the pinned reference directly, without an approved list.** Simpler, but every role would repeat the pins and a bump would touch each role. One list gives one review and one place to see what is in circulation.
- **Let the agent fetch a skill when it needs one.** The model would choose its own equipment at run time, which the level model forbids for tools and which no review would see.
