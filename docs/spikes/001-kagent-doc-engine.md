# Spike 001 — Can kagent run the Doc as well as HolmesGPT?

| | |
|---|---|
| Status | Ready to start |
| Date | 2026-10-16 |
| Timebox | 5 working days |
| Decides | ADR 0007 (confirm kagent, or fall back to a homemade Go engine on ADK Go) |

## Question

With the same model, the same scenery and the same documentary sources, does a kagent `Agent` whose tools are MCP connectors behind agentgateway diagnose incidents **at least as well and as fast** as HolmesGPT, while giving us what Holmes cannot: tools restricted per level, A2A trigger and result, one trace per investigation?

This is a spike: its code is throwaway and lives in `spikes/001/`, outside the product. Its deliverable is a **report** and a recommendation.

## Setup

One k3d cluster, everything pinned in `spikes/001/versions.env`:

| Piece | Version to start from | Notes |
|---|---|---|
| agentgateway | 1.6.x | model route, MCP federation with per-tool authorization, A2A backend, tracing |
| kagent | 0.10.3 (note the state of 1.0 alpha) | Agent, ModelConfig, RemoteMCPServer; A2A on the controller (`/api/a2a/{namespace}/{agent}/`); try both the default runtime and `runtime: go` |
| HolmesGPT (baseline) | 0.45.0 | `toolsets.bash.enabled=false`, `internet` off, same corpus MCP servers, model through the gateway |
| `containers/kubernetes-mcp-server` | latest release | `--read-only`, toolsets limited to core reads, OTel on |
| `giantswarm/mcp-prometheus` | latest release | read-only |
| Corpus MCP servers | from the POC (`content/mcp-corpus`) | the five sources: incidents, runbooks, deployments, vendor, support |
| Prometheus, Alertmanager, OTel Collector, Jaeger | as in the POC | |
| Model | the POC's default (`google/gemini-3.7-flash` via OpenRouter) | same for both engines; a second model if time allows |

Every MCP server is reached **through agentgateway**, by both engines. For Holmes, the native Kubernetes and Prometheus toolsets are the baseline (that is what the POC measured); a second Holmes run with the MCP servers instead isolates the effect of the tools from the effect of the engine.

## Scenarios

At least three, so that the comparison means something:

1. **`proxy-timeout`** (from the POC): DBProxy `idleClientTimeout` 600 s vs application pool 900 s; memory as the false lead. Correct if the proxy idle timeout is named.
2. **`bad-config-rollout`** (new, simple): a deployment rolls out a ConfigMap with a wrong database host; pods fail readiness (`PodNotReady`); the deployments corpus contains the change. Correct if the ConfigMap change and the wrong host are named.
3. **`missing-secret-key`** (new, simple): a new version references a Secret key that does not exist; pods crash-loop (`PodCrashLooping`). Correct if the missing key is named (the agent sees the error in events and logs, never the Secret's content).

Scenarios 2 and 3 are built minimally for the spike; if kagent is confirmed, they become product scenarios (spec 03).

## Doc agent on kagent

- One `Agent` per level (`doc-trial`, `doc-service`), generated by hand for the spike, with:
  - a `ModelConfig` pointing at the gateway;
  - `RemoteMCPServer` tools through the gateway, restricted with `toolNames` to read tools;
  - the investigation instructions: the English prompt of spec 02, plus investigation guidance adapted from HolmesGPT's prompts (credited);
  - an `a2aConfig` with one skill, `diagnose-alert`.
- Trigger: a small Go program using `a2a-go` sends the alert as an A2A message, waits for the task to complete and reads the artifact.

## Measures

For each scenario, each engine (kagent, Holmes native toolsets, Holmes with MCP servers), **5 runs**:

| Measure | How |
|---|---|
| Correctness | scenario rule above, plus a manual read of every diagnosis |
| Cited sources | does the diagnosis cite where it found each fact (pod log, change ID, runbook ID)? |
| Hallucinations | resources, IDs or values that do not exist |
| Latency | trigger to final answer |
| Model calls, tokens, cost | gateway metrics (method of the POC's `mesures.py`) |
| Tool calls | count and list, from traces or gateway logs |

Capability checks, kagent only:

| Check | Pass when |
|---|---|
| Tools by level | `doc-trial` cannot list or call a tool outside its `toolNames`, **and** the gateway refuses a call to an unlisted tool when the agent restriction is bypassed (call forged directly against the gateway) |
| A2A | trigger and result through A2A only; note whether the task carries token usage |
| Traces | one trace per investigation, from the A2A call through kagent to the gateway's `chat` spans and the MCP servers' spans; otherwise note where the chain breaks and whether correlation by an ID is possible |
| Runtime | default vs `runtime: go`: same quality? startup and memory |
| Operability | kagent controller and database footprint; what breaks on restart |

## Go / no-go

kagent is **confirmed** when all of these hold:

1. Correctness on each scenario at least equal to Holmes with native toolsets (and at least 4/5 on `proxy-timeout`).
2. Median latency under 3 minutes from trigger to answer.
3. Tools by level enforced at both layers (agent and gateway).
4. Trigger and result through A2A.
5. Traces joined end to end, or a working correlation by investigation ID.

If 1 or 2 fails, compare with Holmes on MCP servers: if Holmes also drops, the tools are the problem (fix the MCP servers or their descriptions), not kagent. If kagent alone fails 1, 2 or 3, recommend the fallback: a homemade Go engine on ADK Go, behind `engine.Engine` (ADR 0007).
