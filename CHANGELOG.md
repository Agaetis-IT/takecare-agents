# Changelog

All notable changes to TakeCare Agents are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). While the API is `v1alpha1`, breaking changes may happen between minor versions (ADR 0003); they are announced here.

## [Unreleased]

### Added

- The demo's make targets (spec 03, PR 5e): `make demo-up` checks the prerequisites (Docker with at least 4 GB), creates the k3d cluster `takecare-demo` on the pinned k3s with its own kubeconfig, creates the Secrets from the environment or a git-ignored `.env`, installs both charts with the demo profile, and applies the Doc and the `TakeCareDemo` from `demo/manifests`. A second run changes nothing and takes seconds. `DEMO_IMAGES=build` builds and imports the images until the first release. Also `make demo-incident` (refused while an incident or a reset is in progress; prints the expected alert window), `make demo-verdict`, `make demo-screens` and `demo-screens-stop`, `make demo-reset` and `make demo-down`. None of them changes your kube context.
- The demo's corpus and drift (spec 03, PR 5d-2): the `TakeCareDemo` controller writes the five `takecare-demo-corpus-<source>` ConfigMaps, owned by the demo: the healthy corpus, or the incident's dated relative to it. `SceneryReady` reports drift, the POC's lesson. The app (mode, image, environment), the DBProxy's `idleClientTimeout` and a corpus edited by hand are written again and named in a `SceneryDrift` event. The rules Prometheus loaded are compared with the chart's (the new `takecare-demo-rules` ConfigMap, rendered from the same values) and any difference is named in `SceneryReady`; an unreachable Prometheus is noted, not reported as drift. Phase changes are events.
- The `TakeCareDemo` controller (spec 03, PR 5d-1), demo only: the operator runs it with `--demo`, which the chart sets with `demo.enabled`. It deploys `billing-api` (memory growth capped at 360 MB under a 512Mi limit, pool idle timeout 900 s) and the `DBProxy` `billing-db-proxy`. The `takecare.agaetis.fr/incident` annotation sets the proxy's `idleClientTimeout` to 600 s and switches the app to `leaky`. `takecare.agaetis.fr/reset` puts the scenery back to healthy and deletes the Doc's investigations of the app namespace. The status records `incidentStartedAt` when the leaky pod is available, and the `expectedAlertWindow` computed from the app's ratio and the `HighErrorRate` rule. Scenarios other than `proxy-timeout` are refused with `ScenarioNotAvailable`. Every new incident value rolls out a fresh leaky pod. The operator reads the scenery outside its cache and writes it with rights the chart grants by name in the demo namespaces only. The chart value `demo.namespaces` becomes `demo.appNamespace` and `demo.platformNamespace`, and `demo.app.image` names the demo application's image.
- The demo chart (spec 03 and 05, PR 5c): the `demoCorpus` add-on (demo only, it requires `demo.enabled`) deploys one read-only corpus MCP server per source, each with its `TakeCareConnector`: `incidents`, `runbooks` and `vendor` (knowledge), `deployments` (changes), `support` (tickets). The corpus comes from the ConfigMap `takecare-demo-corpus-<source>` that the `TakeCareDemo` controller writes. Each server is reached by the gateway and the operator only and has no egress. The demo Alertmanager now delivers the alerts of `demo-apps` to the Doc's webhook, with the bearer token mounted from the `takecare-alerting` Secret.
- The demo's corpus generator (spec 03, PR 5b): `internal/demo/corpus` composes the content of the five demo sources (deployment log, incidents, runbooks, support tickets, vendor status) for the `proxy-timeout` scenario. Curated seeds carry the scenario's signals, and generated noise from a fixed seed makes the search non-trivial. Dates are in UTC, relative to the incident. Before a corpus is returned, its invariants are checked: the DBProxy change, the past incident and the runbooks that link the idle timeouts, the pool's value never told, the other scenarios neutral.
- The demo's corpus MCP server (spec 03 and 05, PR 5a-2): `takecare-agents-mcp-corpus`, one read-only MCP server per demo source (`<source>_search`, `<source>_get`, `<source>_recent`, annotated read-only) over a JSON corpus mounted from a ConfigMap and reloaded when it changes. Go, built by the repository's Dockerfile with its third-party licenses in the image; behaviour ported from spike 001.
- The demo's application image (spec 03, PR 5a-1): `takecare-agents-demo-app`, the `billing-api` application with the modes `healthy` and `leaky` (the `proxy-timeout` scenario: a 504 ramp, a capped memory growth, the log lines the Doc reads). Go, built by the repository's Dockerfile with its third-party licenses in the image; behaviour ported from spike 001.
- An AlertmanagerConfig for clusters run by Prometheus Operator (spec 02 §1): when `monitoring.coreos.com/v1alpha1` is served, or as forced by `alerting.alertmanagerConfig.create` (`auto`, `true`, `false`), the chart routes the alerts, with no matcher and `continue: true`, to the Doc's webhook with the token Secret. The chart's README says which settings of the Alertmanager resource it needs (its selector, and the namespace matcher strategy). `make chart-template` renders that branch; `test/chart` validates the object against Prometheus Operator's CRD, vendored from v0.94.1 and pinned in `hack/versions.env`.
- The retention of investigations (spec 02): once an hour, the leader deletes the ended investigations (`Completed`, `Failed`, `TimedOut`, `Dropped`) older than the chart value `investigations.retention` (default `168h`), by their completion time, or their creation for a dropped one. A `Queued` or `Running` investigation is never deleted.
- The Doc's publication (spec 02 §4, PR 4c-2a). A completed investigation is published through the Doc's report connector, by the operator, to the destination of the level it was created at: `trial` to `spec.report.trial` or status only, never `on-call`; `service` and `seasoned` to `spec.report.service`; a silent investigation nowhere. The message (Block Kit for Slack, the same as text for the log adapter) carries the header, the diagnosis unchanged, the time since the alert, the trace ID, the trial banner, the connectors the run went without, and the alerts of the incident folded in after the run started; with its usage. Three retries with backoff; the outcome in `status.published`, a final failure as a warning event. `takecare_investigation_duration_seconds` measures alert accepted to diagnosis published. The platform reports the production gap `role-without-report`: a role at the service level without a report connector.
- The usage and cost of an investigation (spec 02 §5, PR 4c-2b): the gateway's metrics read in Prometheus when the run starts and one scrape interval after it ends (chart value `operator.usageScrapeWait`, default 30 s), the difference priced with the model's pricing, `approximate` when the Doc may run investigations at the same time. The diagnosis is published once, with its usage. When the usage cannot be measured (Prometheus unreachable, a counter reset, a run resumed after a restart), the condition `UsageAttributed=False` says why and the message says "usage unknown", never a number.
- The Doc's runs (spec 02 §2, PR 4c-1): a worker on the leader takes the queued investigations, at most the Doc's `maxConcurrent` at once, and only for a Doc that is not suspended, `Ready` and `EngineReady` (a record otherwise waits `Queued`). It records `Running`, the start, the attempt, the engine, the trace ID and the connectors the run goes without (`status.degraded`), then the task ID before following the task. A lost task is started again once within the record's timeout; a new leader follows the runs left `Running` by their task ID. Ends: `Completed` with the diagnosis, `Failed` (`EngineFailed`, `EngineFailedAfterAnswer` with its text kept and never published, `TaskLost`, `StartFailed`, `DocMissing`) or `TimedOut` with the cancellation's result, each with a warning event; nothing is published yet. Every run is one trace: the root span `invoke_agent doc` from the alert's acceptance, with the GenAI and `takecare.*` attributes, the degradation, the outcome and the events `alert.accepted`, `investigation.started`, `investigation.retried`, `investigation.completed`.
- The run half of the engine boundary (spec 02 §2, ADR 0009): `engine.Runs` (start, poll, cancel) implemented for kagent 0.10.3 over A2A with a2a-go v2.6.0. The run goes through the gateway's A2A route, built from the agent's endpoint and never read from its card; it is sent non-blocking, and its task ID is recorded before it is followed (a task whose ID cannot be recorded is canceled). A cut read is retried; only a task the engine no longer knows is lost. At 90 % of the timeout the task is canceled: kagent 0.10.3's python runtime refuses, which is counted. A failure after an answer (`EngineFailedAfterAnswer`) is told apart and counted. Metrics `takecare_runs_total{role,outcome}`, `takecare_run_cancels_total{role,result}`. The Doc's message template (`internal/doc/message.tmpl`), golden-tested.
- The Doc's rendering (spec 02 §2): the `TakeCareDoc` controller checks its connectors, model and level, renders on the gateway one MCP route and one tool policy per connector (read tools only, from the connectors' discovered tools) and the A2A route to its agent, limited to the agent's own path, and renders in kagent the `Agent` (runtime `python`, content-capture switches per Agent, instructions in a ConfigMap) and one `RemoteMCPServer` per connector. A tool reference is never rendered without its allow-list: on kagent 0.10.3 an empty `toolNames` gives every tool. A connector never discovered is not given to the agent; one known but unavailable is, and the Doc says so (`Degraded`). The gateway's policies follow the connectors at once; a re-rendering of the agent waits while an investigation is `Running`, at most until its timeout (`status.renderPendingSince`). `EngineReady` needs the agent card to answer through the gateway's A2A route, with a two-minute start grace. Conditions `MissingConnectorType`, `ScopeNotCovered`, `SingleDocOnly`, `NotImplemented` (seasoned behaves as service); a finalizer removes the engine's objects, and the chart's README says how to finish a deletion without the operator.
- `TakeCarePlatform.status.gatewayURL`, the gateway's in-cluster base URL the roles' routes are served on.
- kagent's agent cards advertise the gateway's root (`kagent.controller.a2aBaseUrl`), so that a client following a card stays behind the gateway.
- The building blocks of a role's rendering (spec 02 §2, ADR 0007, 0008, 0009): the engine boundary's `engine.Agents` and `engine.Engine`, implemented for kagent 0.10.3 (an `Agent` with the `python` runtime, content-capture switches per Agent, instructions in a ConfigMap, one `RemoteMCPServer` per connector, never without its allow-list: on kagent 0.10.3 an empty `toolNames` gives every tool); `internal/routes`, a role's MCP routes with their tool policies and its A2A route limited to the agent's own path; the Doc's instructions (`internal/doc/instructions.md`, golden-tested, HolmesGPT credited in the file); a test that the boundary imports no role and no alert.
- The Doc's trigger (spec 02 §1): `POST /v1/alerts` on every operator replica, behind a bearer token read from the operator's cache (a rotation needs no restart): the generated Secret `takecare-alerting`, kept across upgrades, or the customer's own with `alerting.existingSecret` for `helm template` and GitOps tools. 1 MiB limit, `202` once recorded, `503` on a failure (Alertmanager's resend is idempotent; the metrics count deliveries). Firing alerts in a Doc's scope and matchers become `TakeCareInvestigation`s; deduplication by fingerprint and `startsAt`, cooldown per fingerprint, and **grouping by incident** (namespace plus workload from the alert's labels): later alerts of the same incident are folded into `status.alerts`. Silent alerts, resolved alerts (`resolvedAt`), and the metrics `takecare_alerts_received_total`, `takecare_alerts_ignored_total{reason}`, `takecare_investigations_total{role,phase}`.
- The run queue (`internal/runs`): bounded at 20, oldest first, held by the leader and rebuilt from the `Queued` records after a failover; overflow is `Dropped` with a reason and a warning event.
- API: `RunStatus`, the status every agent role's record shares (spec 06 §3): phase, reason, times, attempts, engine, degradation, usage, trace. `TakeCareInvestigation` is built on it; its phase set is checked by CEL. `AlertRecord` gains `fingerprint` and `workload`, the investigation status `alerts`.
- A README per chart, to read before installing: what can hurt first (uninstalling `takecare-crds`, the Gateway API hook and its modes, the namespace, the external PostgreSQL), the prerequisites on the customer's side, install and upgrade, the security requirements of ADR 0007, private registry, proxy and CA, and a values table generated by `helm-docs` (`make chart-docs`), checked for drift by `make chart-lint`.
- `takecare-agents-mcp-report-slack`, TakeCare's report MCP server (spec 05): one tool, `post_message(destination, blocks)`, posting to Slack's `chat.postMessage` with a token read from a mounted Secret at every call, `auth.test` at startup, every 30 minutes and after an authentication error, the token's state as the pod's readiness (only an authentication error flips it), `Retry-After` honoured on 429, destinations limited to the connector's, and a log mode for the demo. Add-ons `reportSlack` and `reportLog` (exclusive) with the operator-only NetworkPolicy and an egress stated as DNS plus 443 to the outside or the proxy pods. The connector controller watches the add-ons' EndpointSlices (`Reachable=False`, `NoReadyEndpoint` at once); the platform reports `report-log-enabled`. One Dockerfile builds both images (`COMPONENT`); new images follow `takecare-agents-<component>`.
- The connector controller (spec 05, ADR 0008): the gateway's MCP backend per connector, tool discovery and classification (`readOnlyHint` or `act`), overrides recorded in the status with a warning event, and for cluster add-ons the read-only guard checked by `SubjectAccessReview` and the API-discovery probe that restarts a stale `kubernetes-mcp-server` (at most once per 5 minutes). The operator reaches the servers directly and calls a tool only to publish or to probe.
- Add-ons `kubernetes` and `prometheus` (chart values `addons.*`): server, read-only RBAC rendered by the chart, NetworkPolicies (ingress from the gateway and the operator only; egress of `mcp-prometheus` limited to the configured Prometheus), and their `TakeCareConnector`. ConfigMaps are read only when listed in `extraResources`. The gateway itself now admits the operator, the engine namespace and the declared metrics scrapers only.
- API: `extraResources` refuses `secrets`, `pods/exec`, `pods/attach` and `pods/portforward` (CEL).
- `ProductionReady` gap `connector-not-ready`.
- `ProductionReady` on the platform (spec 01): the gaps `no-telemetry-export`, `content-capture-on`, `single-replica`, `gateway-metrics-not-scraped` (a Prometheus probe outside the reconciliation, filtered on the platform's Gateway, cached with a 3-minute validity) and `no-network-policies` (presence, not enforcement), advisory and never part of `Ready`.
- `internal/telemetry`: the operator's trace export over OTLP (gRPC or HTTP) following `spec.observability`, parent-based sampling from `samplingPerMille`, the attribute names of ADR 0006 in `internal/telemetry/semconv` (pinned to the GenAI registry of semantic-conventions v1.37.0; agentgateway 1.6.0 still emits `gen_ai.system`). The gateway's tracing policy samples at the same ratio the traces it starts and keeps the parent's decision otherwise. Outbound HTTP (probe, exporter) trusts `global.caBundle` and goes through `global.egressProxy`, with `noProxy` honoured.
- The platform controller (spec 01): one `AgentgatewayModel` per declared model, one engine model configuration per model through the engine boundary (`internal/engine`, kagent 0.10.3 written as unstructured objects with strict field validation), the gateway's tracing policy, and the platform status (`GatewayReady`, `ModelsReady`, `ObservabilityReady`, `Ready`, `models[].route`). A missing Secret is named and recovers on its own; a Gateway outside the operator namespace and an engine namespace other than the chart's are refused with a reason. The operator's rights are generated Roles per namespace, copied into the chart by `make chart-sync`.
- Charts `takecare-crds` (TakeCare CRDs kept on uninstall, agentgateway and kagent CRDs as dependencies, the ACK `DBProxy` CRD for the demo) and `takecare` (operator, `TakeCarePlatform` rendered from values, the Gateway, kagent and agentgateway as dependencies with the installation requirements of ADR 0007, `values-prod.yaml` template and complete `values-demo.yaml`). Helm 4 is the supported line.
- The operator subcommand `gateway-api-crds`, run by a hook job of `takecare-crds`: installs the Gateway API CRDs embedded in the binary, without Internet access, and never downgrades a cluster's own (`gatewayAPI.install: auto | always | never`).
- kagent 0.10.3 pinned in `hack/versions.env`; `make chart-sync`, `chart-lint`, `chart-template`, `chart-smoke` (a real install and upgrade on k3d) and a `chart` CI job.
- API types and CRDs, group `takecare.agaetis.fr/v1alpha1` (ADR 0003): `TakeCarePlatform` (cluster-scoped singleton `main`), `TakeCareConnector`, `TakeCareDoc`, `TakeCareInvestigation` and `TakeCareDemo`, with the shared `RoleCommonSpec`, CEL validation, printer columns and the `takecare` category. Generated CRDs are in `config/crd`; no controller yet.
- Operator skeleton (`cmd/operator`): controller-runtime manager with health probes and authenticated metrics, no controller yet.
- `Makefile` targets `generate`, `lint`, `test`, `licenses`, `gitleaks`, `build`, `docker-build` and `docker-buildx` (amd64 and arm64).
- `hack/versions.env`, the single place for pinned third-party versions; the agent engine is left out until ADR 0007 and ADR 0010 are settled.
- CI workflow: Go, Python, shell and Markdown linters, SPDX headers, unit and envtest tests, license check, multi-arch image build, gitleaks.
- Proprietary `LICENSE`, generated `NOTICE` and the licensing rules in `docs/licensing.md`.

### Changed

- The operator's image is renamed `takecare-agents-operator` (was `takecare-operator`), following the `takecare-agents-<component>` naming of the images (issue #22). A mirror of the images must add the new name. The Deployment, its ServiceAccount, the RBAC objects, the server-side apply field owner and the leader election ID keep their names, so an upgrade replaces the pods without a second leader or a field ownership conflict.
