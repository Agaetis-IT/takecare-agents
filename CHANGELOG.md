# Changelog

All notable changes to TakeCare Agents are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). While the API is `v1alpha1`, breaking changes may happen between minor versions (ADR 0003); they are announced here.

## [Unreleased]

### Added

- The Mécano's API (spec 12), ahead of its controller: the kinds `TakeCareMecano` (short name `tcmecano`) and `TakeCareMaintenance`, with their CRDs in the `takecare-crds` chart. A Mécano needs at least one `cluster` and one `code` connector, and binds at most one `propose`, one `copy`, one `history` and one `map` connector, four `releases` and sixteen of the others; its schedule is weekly by default (`0 5 * * 1`, UTC) or `none`; its maintenances run 15 minutes at most and report certificates 30 days ahead by default; the repositories its plans may target name its `propose` connector. Its name is at most 47 characters, a maintenance's at most 63 without a dot, refused at creation. A maintenance's spec is immutable and its status bounded (200 components, 100 objects on a removed API, certificates and GitOps applications each, 50 findings, a plan of 20 steps and 16 pull requests). `RoleRef` and the Ranger's `spec.models` accept `TakeCareMecano`. Nothing creates or runs a maintenance yet.
- The connector type `code`, for the customer's Git (spec 12 §5), and `spec.propose` on a connector: the Secret of a propose add-on's write token and the repositories (GitHub or GitLab, an `https` API URL, `owner/name` or a GitLab project's path) it may open pull requests on, on a `code` connector served by an add-on only. The propose server comes with the next lot.
- The code add-on (spec 12 §5), `addons.code`: our server `takecare-agents-mcp-code` and the connector `code`, with four read tools over one to sixteen of the customer's Git repositories, each one branch, polled and cloned again at depth 1 when its head moves, so that only the head's files stay in memory (the chart's values say how to size the memory limit), with a read-only HTTPS token or SSH deploy key (its `known_hosts` required) mounted from a Secret. `repositories_list` gives each repository's served revision; `manifests_index` gives, per YAML document, its path, kind, namespace, name, the images its pod templates run and the Helm charts it names (`Chart.yaml`, Flux `HelmRelease`, Argo CD `Application`) and a Kustomization's image overrides (Kustomize `images`, Flux `spec.images`), never a value; `files_list` lists paths and sizes; `file_get` returns a file of at most 256 KiB and is a content tool, given to a role only when its `contentTools` list it. No tool reads a path outside the repositories, a symbolic link or a submodule. Its ServiceAccount has no Role and no token; its ingress is the gateway and the operator, its egress DNS and TCP 443 (and 22 for an SSH remote) outside the cluster, or the proxy pods. Off by default. The release publishes the new image, eight images in all.
- The operator's rights on the Mécano's kinds in `takecare-system`, decided by the product owner: `get`, `list`, `watch` and `update` on `takecaremecanos`, `update` on `takecaremecanos/finalizers`, `create`, `delete`, `get`, `list`, `patch` and `watch` on `takecaremaintenances`, and `patch` on both kinds' `status`.
- The chart value `maintenances.retention` (8760h), given to the operator as `--maintenance-retention`: how long an ended maintenance is kept. The sweep that applies it comes with the Mécano's runner.

## [0.5.0] - 2026-11-26

The Talkie and Kiné release: the `takecare` command, the teams' console (status, discover, review, validate, init), the Kiné, which reviews the Doc's investigations after each incident up to `Practitioner`, and a first step towards grounds without Kubernetes, the `cloud` connector type for Azure, in the API only. The API stays `v1alpha1`; it gains the kinds `TakeCareKine` and `TakeCareReview`, the connector types `history` and `cloud`, and new fields, and refuses nothing it accepted before.

**Before upgrading from 0.4.x**, read the upgrade notes below. In short:

- a role's MCP path on the gateway now holds the role's kind, `/mcp/<namespace>/<kind>.<role>/<connector>`: a client of your own that calls a role's MCP route by its old path gets a 404 (Fixed);
- ended investigations are kept 90 days instead of 7, and at most 2,000 (`investigations.maxKept`), the oldest deleted first past that count; set `investigations.retention` back to `168h` if etcd's room matters more than the Kiné's view of recurrences (Changed, Added);
- the operator's rights gain the Kiné's kinds in the release namespace, and its run-time read-only guard now checks every add-on connector's ServiceAccount: a right bound by hand to the history, Map, report or corpus server's account makes its connector not Ready (Added, Changed);
- a Kiné that sets no `schedule` gets a weekly periodic review (Monday 06:00 UTC); `schedule: none` plans none. The demo's Kiné sets `none` (Added);
- the `takecare` command warns, on one line of stderr and never as a failure, when it is more than one minor version apart from the cluster's TakeCare (Added);
- `takecare init` writes `.takecare/answers.yaml` at version 2, where the Secret questions are `map.secretRef`, `report.secretRef` and `model.secretRef`. No release shipped `init` before; an answers file written by a build of `main` before 0.5.0 (version 1, with `map.secret`, `report.secret` and `model.secret`) is refused: rename those three ids and set `version: 2`, or run `init` again (Added).

### Added

- A Kiné can do without its periodic review: `schedule: none` plans none, leaves `nextReviewTime` empty and reports `ScheduleValid` True with a message saying "no periodic review"; the reviews after an incident and on demand go on (spec 11 §3). A Kiné that sets no schedule keeps the weekly default (`0 6 * * 1`).
- The `takecare` command (spec 13), its first lot: `takecare status` shows the platform, each role with its level, readiness and blind spots, the connectors with their tools by class, and the newest surveys and investigations, in text or JSON; its exit code is 1 when something is not Ready, for scripts. `takecare version` prints the version and commit. The command only reads the cluster, with the user's own rights (get and list on the TakeCare kinds, listed in `docs/how-to/takecare-command.md`), and never writes into it or into the kubeconfig. Install it with `go install github.com/agaetis-it/takecare-agents/cmd/takecare@<version>`.
- Each release attaches the `takecare` command for Linux, macOS and Windows, on amd64 and arm64: one archive per platform with the binary, `LICENSE`, `NOTICE` and the third-party license texts, one SPDX 2.3 SBOM per binary, and a checksums file covering them (spec 13 §8). `go install github.com/agaetis-it/takecare-agents/cmd/takecare@<version>` still works; the release dry run now checks that `go.mod` keeps it working. `docs/how-to/takecare-command.md` shows how to check an archive before unpacking it.
- `takecare review` turns a survey's proposals into Map files: one screen per proposal with its evidence and the diff against the local file, or `--accept <ids>|all` and `--skip <ids>` without a terminal. An Add writes the entry's file, an Update replaces it and keeps its `provenance`, `created` and `owner`, a Remove deletes it and the relations other entries declare to it. The whole result is checked with the Map server's checks before anything is written. The decisions are recorded in `.takecare/review.yaml`, so that a proposal decided once is shown again only when its entry changed. The files are committed on a local branch with your own `git`, identity and signing; nothing is pushed. It reads the cluster with get and list on the Intendants and surveys, and get on the survey's ConfigMap.
- `takecare discover` shows an Intendant's newest survey: its phase, trigger and age, the Map revision it surveyed against beside the one the map connector serves now (saying when the survey predates the served Map), its proposals by action and source, each layer's counts with what it could not read, and its blind spots, in text or JSON. It then prints the `kubectl create` command that starts a new survey, with the Intendant's name and namespace filled in; it creates nothing itself. It reads the cluster with get and list on the Intendants, surveys and connectors.
- `takecare validate` checks a Map directory offline with the Map server's own checks and reports every fault at once, each with its file; its exit code is 1 when the Map does not validate, for a CI job on the Map's repository.
- `takecare validate --questions <dir>` checks question files, the format `takecare init` reads (spec 13 §4.2), without asking or rendering anything: every fault of every file at once, each with its file (an unknown field or kind, an id defined twice, a `when` naming an unknown question or part of a cycle, a template that does not parse, an output path outside the repository, under `.git/` or `.takecare/`, or not a `.yaml`, `.yml` or `.md` file).
- `takecare init` asks factual questions about the ground (spec 13 §4.1) and writes the first files of an install into a Git working copy: the Map's first entries (environments, teams, the Prometheus service; declared and proposed, for a person to validate), the chart's values for the platform and the four add-ons, the Doc and the Intendant at level Apprentice, a connector to an external runbook source, and `.takecare/answers.yaml`. Each question shows why it is asked and accepts "I don't know", which leaves a `TODO` in the files; none asks for a secret value. A question about a credential asks for the name of the Kubernetes Secret, not its content, in three fields (the Secret's namespace, its name, the key in it). Three questions come prefilled with the usual answer, for the person to confirm or change: the operator's namespace (`takecare-system`), the alert source (Prometheus Alertmanager) and the Prometheus service (`monitoring/kube-prometheus-stack-prometheus`). A question file may give a question a `default`, checked like an answer when the file is loaded; a Secret question takes none, and `--answers` never uses one. `--answers <file>` runs it without a terminal, `--questions <dir>` adds question files, and `--accessible` (or `TAKECARE_ACCESSIBLE=1`) asks with line prompts for screen readers; `--no-color` turns the forms' colors off. Run again, it asks only what is new, shows the diffs, and never overwrites a file a person edited without asking (or `--overwrite`). The files are committed on a local branch with your own `git`; nothing is pushed.
- API: a connector type `cloud` for a ground without Kubernetes, with `spec.reach.azure`: a tenant and its subscriptions, each whole or narrowed to resource groups (ADR 0021). The API checks the IDs, Azure's resource group naming rule and uniqueness regardless of case; it takes up to 64 subscriptions and 32 groups per subscription. A Doc binds such connectors in `spec.connectors.cloud`, and an entity with an `azure` source in the Map is covered when a given connector's reach holds it. No add-on serves the type yet: `cloud` is a first step, and no TakeCare server for it ships before a 1.x release. The Resource Graph importer that will survey such a ground is designed in spec 10 §4.1 and built, not yet wired into the survey.
- The Kiné's API (spec 11), ahead of its controller: the kinds `TakeCareKine` (short name `tckine`) and `TakeCareReview` (`tcreview`), with their CRDs in the `takecare-crds` chart. A Kiné needs exactly one `history` connector; its name is at most 49 characters and a review's at most 63, refused at creation. A review's spec is immutable and its status bounded (20 actions, a 4 KiB problem statement, a 16 KiB post-mortem draft). Nothing creates or runs a review yet.
- The connector type `history`, for TakeCare's own investigations and reviews (spec 11 §4). Its server comes with the next lot.
- The history add-on (spec 11 §4), `addons.history`: our server `takecare-agents-mcp-history` and the connector `history`, with four read tools over the investigations and reviews of the release namespace. `investigations_list` and `reviews_list` return state only, never a diagnosis or a review's text, and leave silent (bench) records out. `investigation_get` and `review_get` return the model's text and are content tools, given to a role only when its `contentTools` list them. The server reads with its own ServiceAccount, decided by the product owner: one Role in the release namespace with `get`, `list` and `watch` on `takecareinvestigations` and `takecarereviews`, no ClusterRole, the token mounted on the pod only. Its ingress is the gateway and the operator, its egress the API server only (TCP 443 and 6443). Off by default, on in the demo profile. The release publishes the new image, seven images in all.
- The operator's rights on the Kiné's kinds in `takecare-system`, decided by the product owner: `get`, `list`, `watch` and `update` on `takecarekines`, `update` on `takecarekines/finalizers`, `create`, `delete`, `get`, `list`, `patch` and `watch` on `takecarereviews`, and `patch` on both kinds' `status`.
- The Kiné's controller, its gateway layer (spec 11 §2, §9): a `TakeCareKine` gets its routes on the gateway, decided by the product owner. One MCP route per bound `history`, `knowledge`, `tickets`, `changes` and `map` connector, whose allow-list is the connector's read tools plus the content tools the Kiné lists in `contentTools`, the same at `Apprentice` and `Practitioner`, with no argument rule; none for `report`. A route to its agent over A2A, and a route to its model. The Ranger's per-model cap and its allowed-models deny cover the Kiné's model route: `TakeCareKine` joins the kinds `spec.models` accepts. A Kiné without a usable history connector says `HistoryConnectorMissing`; the later of two Kinés whose scopes overlap says `ScopeOverlap` and renders nothing.
- The Kiné's agent (spec 11 §6, §7): a `TakeCareKine` gets its kagent `Agent` `takecare-kine-<name>`, its model configuration reaching the model through the Kiné's own model route, and one tool server per routed connector with the route's allow-list. Its instructions follow its level: at `Apprentice` the problem, its recurrences and the earlier actions still undone (`Open` or `Unknown`), with no new action and no post-mortem; at `Practitioner` new actions and a post-mortem draft too. A Kiné not given `investigation_get` is told it cannot read a diagnosis. The Kiné is `Ready` once kagent runs its agent. kagent takes at most 20 tool servers on an agent: past that, `EngineReady` is False with reason `TooManyToolServers`, giving the count, and no agent is rendered. A new rendering of the agent waits while a review of the Kiné is `Running`, at most until its `review.timeout`, with `EngineReady` reason `RenderPending` and `status.renderPendingSince`; the gateway's routes and policies never wait. Nothing creates or runs a review yet. No new gateway rule and no new operator right.
- The Kiné's reviews run (spec 11 §6): a `TakeCareReview` created by hand is `Queued`, takes a controller reference to its Kiné, and runs on the Kiné's agent, one review per Kiné at a time, oldest first; another Kiné's reviews do not wait. A review that waits says why in `status.reason` (`KineBusy`, naming the running review, or `QueueFull`, with one warning event on the Kiné). The agent's answer is read strictly (one fenced JSON block against the answer's schema): the problem, its recurrences, the actions with stable ids (`<review>-<n>` for a new one; an earlier one keeps an id another review of the Kiné holds, silent reviews left out, or its knowledge record's `<record>/<n>`, otherwise it gets a new id and a blind spot) and, at `Practitioner`, the post-mortem draft; what exceeds a bound is cut and counted. An answer that cannot be read leaves the review `Completed` with nothing recorded and the reason "the review's answer could not be read"; a review that does not finish or asks a question ends `Failed` with a fixed phrase, and a review whose Kiné does not exist ends `Failed` naming it, its usage said not measured. A review that reaches the runner while its Kiné is suspended or not `Ready` ends `Failed` with the reason "the Kiné is not ready to review", and one that reaches it while the gateway is not ready ends `Failed` with the reason "the gateway is not ready": neither waits for them. A review left `Running` by a stopped operator is followed again on its task; one nobody runs ends `Failed` (`Abandoned`) past its `review.timeout`.
- A Kiné's review measures its usage on the Kiné's own model route, one scrape interval after the run (model calls, tokens, estimated cost; approximate when the Kiné's previous review did not finish), and says why when it cannot (`UsageAttributed`). It lists its blind spots: a bound connector that is not `Ready`, a content tool `contentTools` does not list, a period that starts before the oldest investigations kept. An earlier action keeps the id an earlier review of the same Kiné gave it. The backstop's bound counts the scrape wait.
- The Kiné's triggers (spec 11 §3): the Kiné watches the investigations of its namespace and creates one `TakeCareReview` per incident once its investigations are due. An investigation is due when it is in the Kiné's scope, not silent, `Completed` with a diagnosis after the Kiné was created, and its alert resolved or `review.grace` (24 hours by default) passed since it ended, and no review of the Kiné names it yet. Investigations of one incident key due together give one review, at most ten investigations each, oldest first. The review's name is a hash of the Kiné and the oldest investigation, so a trigger seen twice creates one review. The schedule (`spec.schedule`, in UTC, weekly by default) gives one periodic review per due time, shown in `status.nextReviewTime`; a due time that meets a review in flight waits in `status.pendingTrigger`, and due times that pile up give one review. `ScheduleValid` says when the schedule is refused. A suspended or not `Ready` Kiné creates no review; a review that failed because the Kiné or the gateway was not ready no longer counts once the Kiné is `Ready` again, so its investigations are reviewed then. No new operator right: the operator already reads the investigations for the Doc.
- The Kiné publishes a completed review (spec 11 §8) through its report connector: the problem, the recurrences, the first ten corrective actions with their state, at `Practitioner` where the post-mortem draft is (the draft itself is not posted), and the investigations, usage and trace ID; Block Kit for Slack, the same as text for the log adapter. A review is posted once (idempotency key `review/<uid>`, the Doc's retries and 3-minute bound), its outcome in `status.published`, a final failure also as a `PublicationFailed` event. It goes at the lower of the review's level and the Kiné's level now, so that an Apprentice Kiné never reaches the `practitioner` destination, even for a review made by hand at `Practitioner`. A `Failed` review posts nothing; a silent one, one that found no problem, recurrence or action, or one with no destination at its level says why in `status.published`. A new leader posts what its predecessor left unpublished, one per second.
- The Kiné's metrics (spec 11 §11): `takecare_reviews_total{kine,trigger,result}`, the reviews ended per Kiné, with result `completed`, `unreadable` (completed, the answer not read), `failed` or `abandoned`; and `takecare_review_actions{kine,state}`, the corrective actions of each Kiné's last completed review by state (`open`, `done`, `unknown`). Their series go when the Kiné goes. The Kiné's `status.lastReview` and `lastReviewTime` name the last review started.
- The demo's Kiné (spec 11 §12), `demo/manifests/kine.yaml`: `make demo-up` applies it with the Doc and the Intendant and waits for it to be `Ready`. It reviews the demo's investigations at `Apprentice`, on `demo-apps`, with the history connector, the corpus's incidents and runbooks as knowledge, the support tickets and the deployment log, and `investigation_get` and `review_get` as content tools. Its `review.grace` is 2 minutes, in the demo only, so that a review follows `make demo-incident` before `make demo-reset` deletes the investigations. It has no periodic review of its own (`schedule: none`). `make demo-verdict` now also waits for the Kiné's review of the investigation and prints its phase, problem, recurrences, action counts, publication and usage. The end-to-end test lifts the Kiné's suspension last, at `Practitioner` with the review destination, and checks its review of the Doc's investigation against a hand-written fake-model answer: `Completed` with the recurrence, the earlier undone action, a new one and the post-mortem draft, its usage attributed, and one message on the fake Slack matching a golden file.
- The Kiné bench (spec 11 §12), `make demo-bench-kine N=5 BENCH_MIN=5`: N silent reviews at `Practitioner` of a fixed investigation, the demo Kiné raised to `Practitioner` for the series (bound to the report connector, with no destination) and restored on every exit, the Doc's recorded diagnosis of the proxy-timeout incident, each scored on three items: the recurrences name `INC-2024-0312`, the actions hold that incident's undone automated check (`Open` from its record or `Proposed`), and no action proposes raising the memory limit. The report gives each run's duration, model calls, tokens and cost, and the gateway's guard counters. `BENCH_MAX_COST` stops the bench before a cap in USD; `BENCH_CHAIN=1` reviews live Doc runs instead and does not count for the bar. The bar at a release is five out of five (`docs/release.md`).
- `takecare status`, `discover` and `review` warn when the command and the cluster's TakeCare are more than one minor version apart, kubectl-style: one line on stderr, or a `versionSkew` field with `--output json`, never a failure. The cluster's version is the one the chart writes on the `TakeCarePlatform`; a dev build, or a platform the command cannot read, gives no warning. No self-update and no call outside the cluster.
- The chart value `investigations.maxKept` (2000): past that count, the oldest ended investigations are deleted first, whatever their age. And `reviews.retention` (8760h): each Kiné keeps its newest ended review however old it is.

### Changed

- CI skips its heavy jobs (unit, golden and envtest tests, the image build, the e2e, the chart smoke, the guard corpus, the release dry run, the site build) on a pull request when every file of the push, or of the whole pull request, is a bench report, documentation, a root Markdown file or, for the Go and cluster jobs, the site; `CHANGELOG.md` still runs the release dry run and the site build. The rule of the push applies only when the same job passed at the previous head (read with `checks: read`), otherwise the whole pull request decides. The jobs still report, so the required checks pass; a push to `main` runs everything, and lint, DCO, gitleaks and licenses always run.
- The product site describes 0.5.0: each delivered role's card shows the highest level the product can do, in words (Apprentice, Practitioner, Expert), instead of a version, and its page says what that level does and what the next one will add; the Kiné and its Rehab are delivered; the Talkie now names the teams' console, the `takecare` command, delivered in part; the alert relay becomes a new card, the Whistle, not built yet; the cloud connector type for Azure; and the roadmap. ADR 0017, 0018 and 0021 get a dated note on the rename.
- The alert intake finds an alert's earlier investigations, for its cooldown and its incident, through an index of the operator's cache instead of listing the namespace's investigations from the API server at every alert, which cost a read of up to `investigations.maxKept` records per alert. Deduplication, cooldown and grouping are unchanged, including for a record this replica created a moment before that the cache does not show yet.
- The operator's run-time read-only guard (`ReadOnlyGuard`) now checks the ServiceAccount of every add-on connector, not only the `cluster` ones: a right the guard forbids, bound later to the history, Map, report or corpus server's account, makes its connector not Ready.
- A blind spot for an entity with no source a connector can read now says "no kubernetes or azure source in the Map", instead of "no kubernetes source".
- Ended investigations are kept 90 days by default (`investigations.retention: 2160h`) instead of 7, so that the Kiné can see recurrences. Two thousand investigations with their diagnoses weigh tens of MiB in etcd. The upgrade deletes nothing more than before.
- a2a-go 2.9.0. A failed read or cancellation of a run's task is still labelled with its HTTP status (404, 503…) in the operator's metrics and logs: the status is now taken from the response itself, no longer from the client's error text, which this version changed.

### Fixed

- **A role's MCP path on the gateway now holds the role's kind; breaking for a client of your own on the old path.** The path is `/mcp/<namespace>/<kind>.<role>/<connector>` (for example `/mcp/takecare-system/doc.main/prometheus`), instead of `/mcp/<namespace>/<role>/<connector>`. Two roles of different kinds and the same name in one namespace, a Doc and an Intendant both named `main` for instance, shared one path: their routes conflicted on the gateway, and one role could be served with the other's allow-list. Route names, labels, backends and every policy stay the same; the upgrade moves each route to its new path, then points the role's agent at it. A client of your own that calls a role's MCP route by its old path gets a 404 and must use the new one.
- When a role's connector, model or A2A route is removed, the operator deletes the gateway route before its policies and backend. Until now it deleted the policies first, which left a short window where the gateway served the route without its allow-list or argument rule.
- The connector manifest printed by the `takecare-cluster` chart's install notes now carries `cluster.extraResources`. The inventory opt-ins granted on a workload cluster (kagent `agents`, `sandboxagents`) are then declared on the administration cluster too.
- `make demo-up` with `DEMO_IMAGES=build` stops with the reason when `make docker-build` or `k3d image import` fails. Before, it went on to the install and failed later on an `ImagePullBackOff`.

## [0.4.0] - 2026-11-24

The corrections release: the Ranger's guards scan what tools return, the operator's own rights hold only what its code calls, a customer's MCP server is reached with its credentials and its tools are trusted only once listed, every survey and investigation reaches an end a reader can see, a publication is posted once, and kagent moves to 0.10.6 and agentgateway to 1.7.0. The API stays `v1alpha1`; new bounds refuse only values that never worked.

**Before upgrading from 0.3.x**, read the upgrade notes below. In short:

- an inline `kagent.database.postgres.url` is refused: move it to a Secret mounted as `urlFile` first (Security);
- the tools of a customer's MCP server declared by `url` become `act` until its connector's `spec.tools` lists them as `read` (Security);
- the chart's Gateway listener takes routes from the release namespace only, and the kubernetes MCP server drops four tools our RBAC never let succeed (Security);
- names past the new bounds are refused at creation (a Doc 50 characters, an Intendant 44, a connector or a demo 63), as are a schedule with `TZ=` and connector slots past 16 names; a stored object keeps working where it did and says why where it did not (Changed);
- a report server of your own declared by `url` must accept the new `idempotencyKey` argument (Changed);
- `RequestsMasked` is now a `Normal` event (Changed); an upgrade restarts the gateway's controller and proxy, the kagent controller and the agents' pods (Changed).

### Added

- Each release attaches an SPDX 2.3 SBOM per image and architecture (twelve files, `takecare-agents-<image>-x.y.z-linux-<arch>.spdx.json`), read from the published image: the Go modules compiled into the binary and the base image's Debian packages. They are covered by the release's attestation (`gh release verify-asset`) and never committed.
- The Intendant's inventory lists the kagent `SandboxAgent`s in its scope, as items of kind `Agent`, through a `kubernetes` connector whose add-on has the new opt-in `{group: kagent.dev, resource: sandboxagents}` in `extraResources` (get, list and watch in the declared namespaces), separate from the `agents` one and off by default. Without it, the inventory layer says "sandbox agents in scope cannot be listed: the kubernetes add-on has no kagent.dev sandboxagents rule", so a survey of an installation without the opt-in has one more not-seen line, and a Practitioner digest counts it. An `Agent` and a `SandboxAgent` of the same name in one namespace make one item (spec 10 §8). The default RBAC and the `agents` opt-in are unchanged.
- `takecare_surveys_total{result}` counts the surveys that ended, once each: `completed`, `failed`, or `abandoned` when the operator ended a survey whose end was never written (spec 10 §10).
- A survey the operator creates records the settled registrations it saw (`spec.registrationSet`, at most 200 entries).
- The dump (`hack/dump.sh`) covers what it used to miss. It keeps the operator's log from before the e2e restarts it. It says in its README which pods' logs it could not read and why. On a cluster where the charts never installed, it records the hook Jobs' pod events and logs, each node's images (names and tags) and what is absent. The e2e also dumps when its setup fails, and the chart smoke when its checks fail. `make demo-up` names the hook Job pod's events when an install fails, instead of helm's bare "Job … not ready".
- The long runs (the e2e, the chart smoke, both benches, the guard corpus capture) say at their end whether the machine slept during them, from macOS's power log: "no sleep during the run", or "INVALID: the machine slept from … to …" and exit 2 whatever their checks said. A bench report written before is marked invalid in its own file, and a dump names it in its README. A closed lid's maintenance wakes do not end a sleep, and a run that starts inside a sleep is invalid too. Elsewhere it says the power log was not checked.

- `make clean-local` lists the images the demo, the e2e and the chart smoke built on the machine, now labelled `org.agaetis.takecare.local=true` with their source hash, and removes them only with `CLEAN_LOCAL=remove`. It never touches an unlabelled image, the current tree's, the running demo's or a running smoke's. `make test` leaves envtest's binaries writable, so that a worktree's `bin/` can be removed.
- `TakeCareSurvey` records what the operator observed when it created it: `spec.registrations` (the settled-registrations digest) and `spec.reason` (why it was created). `TakeCareIntendant` gains `status.registrationsSince`, the time the current registrations were first seen. All three are additive.

### Fixed

- The operator's MCP client declares one protocol revision, `2025-11-25`, to every server. Before this fix it declared go-sdk's default (`2026-07-28` at v1.8.0, the stateless revision, with a fallback revision of go-sdk's choice), so that a go-sdk bump would silently change the protocol spoken to every MCP server. Every server TakeCare pins serves `2025-11-25`; a customer's server on an older revision still answers with its own. Each call still opens its own session: four requests a call instead of two on a stateless server, a fraction of a millisecond on a local loopback.
- `make demo-verdict` prints the investigation's usage (input and output tokens, estimated cost). Before this fix it read the record as soon as the investigation ended, before the operator read the gateway's metrics one scrape wait later (30 s by default), and printed "usage: not measured". It now waits up to 120 s (`USAGE_WAIT_SECONDS`) for the record's `UsageAttributed` condition, then prints the usage, or why it was not measured, or that it was not recorded in time.
- A diagnosis or a digest is no longer posted twice when the report server answers after the operator's deadline. Slack could receive the message while the operator's call timed out, and the operator's retry posted it again. The report server now remembers each publication's key, with its first result, for an hour (up to 1,000 keys, in memory: a restarted report server has forgotten them), and a repeated key posts nothing (spec 05, "Publishing once").
- Slack's permanent errors are no longer retried: `channel_not_found`, `not_in_channel`, `is_archived`, an authentication error and every other error Slack answers apart from its rate limits and transient failures end the publication at the first attempt, and the record's reason and the `PublicationFailed` event name the error (no token, no message content). Before this fix, the operator tried four times over 14 seconds whatever the error, and the report server waited out a `Retry-After` inside the call, past the operator's 30-second timeout.
- Names in a published message can no longer become Slack markup: every `mrkdwn` text is sent `verbatim`, so Slack turns no URL, channel name or mention it was not given as markup into a link, and the Doc escapes `&`, `<` and `>` in the alert names and the usage line under a diagnosis, as it already did in the diagnosis.
- An Intendant that names one connector in two slots (for example a connector of types `cluster` and `metrics`, named in both) now renders one stable route for it. Before this fix, each slot wrote its own allow-list and argument rule for the same route in turn, at every reconcile, and each write started the next reconcile. So the allow-list changed continuously between the two slots' lists, one of them refusing every tool while the argument rule was not proven, and the operator deleted and recreated the `get_rules` argument rule at each pass. In about 6% of the samples taken under envtest, the allow-list admitted `get_rules` while no argument rule existed: a `get_rules` call could then pass the gateway with any arguments, `prometheus_url`, `org_id` and `file` included. The agent was also given `get_rules`, which spec 10 reserves to the operator. How much of those windows agentgateway actually served was not measured. Now the route's allow-list is the union of what each slot allows, `get_rules` is never on the agent, and, while the route is kept, the operator writes the argument rule before an allow-list that admits `get_rules`, and removes it after; this order also holds for a connector in one slot. The Doc was not affected. Decided with the product owner.
- Deleting an Intendant named with 45 to 63 characters, or a Doc named with 51 to 63, now completes. Before this fix, the operator looked for the role's tool servers with the engine agent's name as a label selector, which the API server refuses past 63 characters: the deletion failed at every attempt, the finalizer stayed, and the role's routes and model configuration stayed with it. A name past 63 characters labels no tool server, so there is none to look for.
- The Intendant's alerting layer reads past the metrics add-on's cut. mcp-prometheus cuts `get_rules`' answer at 50,000 characters, and before this fix a cut answer gave no alerting rule at all, only a line saying so: on a Prometheus with many rules, the layer read none. Now the import reads again by name the rule groups the cut answer printed, eight a call and at most 128 groups, once, and says which rules it could not read: those after the last group read, the groups whose name it may not ask for (counted, never named), and any group whose own answer is cut again. **The gateway's rule on the metrics route is widened** to let this through: `get_rules` may now carry `rule_group`, a list of 1 to 8 group names of 1 to 128 letters, digits, `_`, `.`, `:` and `-`; every key refused before stays refused (`prometheus_url`, `org_id`, `file`, the canary's). It is also narrowed: an empty `rule_name` list, or a `rule_name` that is not a list (an object was admitted by its keys), is now refused. The rule's text is in spec 10 §8.
- A survey whose end was never written no longer stays `Running` for ever. Before this fix, when the operator could not write a survey's outcome (a status write that failed), the survey stayed `Running` until someone deleted it. Now, once it is past its bound (its start, twice the pass deadline, one scrape interval and 40 seconds) and no runner holds it, the operator ends it `Failed` with reason `Abandoned`, `UsageAttributed` False (`NotMeasured`) and one `Abandoned` Warning, as it already did for investigations. A survey the runner holds is never ended this way, and after a restart a survey left `Running` is still run again.
- A `Registration` survey's reason says what changed ("agent kagent/takecare-doc-east removed; connector east added") instead of "the registrations changed", so that a reader can see why the Intendant looked again.
- A timed-out run's reason no longer ends with the raw text of its last failed read. Before this fix, when the engine's share of the timeout ended a Doc's run or an Intendant's pass, the reason could end with that text, which could quote a response body. Now it holds what the follow saw: the last reads' failures by HTTP status or class ("the last 12 reads failed (HTTP 404)"), the last read that found the task working, or a pause of the follow. A failed cancellation is named by its status or class the same way. A counter, `takecare_run_reads_total`, counts the reads by result.
- `make demo-up` imports the images a recreated cluster lacks. Before, it skipped the import when the image tag it last built was unchanged, even in a cluster deleted with `k3d cluster delete` and created again: the chart's hook Job then waited for an image no node held, and the install failed with "Job … not ready". It now asks the cluster's nodes for each image and imports the missing ones. The tag it last built remains a build cache only.

- The Intendant says when `spec.contentTools` lists a tool that no connector given to its agent exposes, as the Doc does: in `ConnectorsReady`'s message and in one `ContentToolUnknown` warning, instead of dropping it silently. Its import checks every entry it proposes against the Map's schema, as the agent's proposals already were: an entry the Map would not load is not proposed, and the survey's layer names it. The Intendant's and the Doc's instructions now forbid asking a question (kagent gives every agent `ask_user`, and no one answers), and a survey whose agent pass asked one anyway says so, never the question.
- A survey is never lost or left unexplained in its queue. Before this fix, a survey that did not fit in the full survey queue, or that the runner could not read, stayed `Queued` and ran only at some later event. Now it is tried again, a `Queued` survey is put back in the queue within a minute, and a waiting survey says why in `status.reason`: `IntendantBusy` (its Intendant runs another) or `QueueFull` (with one `QueueFull` event on the Intendant). Every write of a survey's status now applies to the state it finds, under an optimistic lock: a late write no longer overwrites a newer one, for example a task recorded after the survey's outcome.
- An investigation always reaches an end a reader can see. Before this fix, a run whose start failed, or whose Doc was deleted, ended `Failed` without its `UsageAttributed` condition; a new operator leader left an ended record without it when the previous one stopped while reading the usage; and a `Running` record whose end could not be written stayed `Running` until a leader change. A reader waiting for the usage, the accuracy bench among them, waited forever. Now every end writes `UsageAttributed` (`False`, `NotMeasured`, with why, when the usage is unknown); the operator's controller ends a `Running` record nobody follows past its timeout's bound as `TimedOut`, reason `Abandoned`, with a warning event; a `Queued` record says why it waits in `status.reason` (`DocNotRunnable` with its Doc's own conditions, or `WaitingForSlot`), and one that left the run queue is put back within a minute. An Intendant's survey also says in status when its pass's usage is unknown. The bench run that did not settle on 2026-11-19 is not explained (its cluster was deleted before anything was read); if it recurred, the bench would now dump the cluster's state, and the record would show which of these ends it reached.
- The Intendant decides from observed state when a survey is due (spec 10 §3). Before this fix, every change of a bound connector or an engine agent gave its own survey, so an install gave a burst of surveys. An agent pass skipped because the agent was not ready was never run once the agent was ready. The first survey ran with its import only before an expected agent could answer. And the operator saw the agent turn ready only at its next 30 s poll, and not at all when it later stopped being ready. Now registrations count once their status has caught up with them and have held for 60 s. A failed survey is not run again until something changes or the schedule is due. An owed pass gives one survey that says why. The first survey waits up to 5 minutes for the agent, saying so in `EngineReady`. The operator follows the agent's readiness as it changes.
- The Ranger masks social security numbers with patterns of TakeCare's own, in place of agentgateway's `Ssn` builtin, which took any nine-digit run: the nanosecond fraction of an alert's `activeAt` in what the metrics connector returns, about a dozen masked requests in each Doc investigation. The patterns take the US number written with its dashes and the French NIR (as on the card or without spaces), and leave timestamps' fractions, resourceVersions, sizes and counters alone. What the model reads in place of a number is now `<masked>`, not `<SSN>`. Spec 09 §4 lists what is missed (a US number without dashes, temporary French numbers) and what is taken by mistake (some fifteen-digit runs). Decided by the product owner (ADR 0020).
- The Intendant's agent is no longer re-rendered while a survey of it is running: kagent 0.10.6 restarts the agent's pod on any change of its rendering, and the pass's task was lost with it. The new rendering waits, at most until the survey's pass deadline, and `EngineReady` says so with reason `RenderPending`, naming the survey; `status.renderPendingSince` (a new status field, additive) says since when.
- A survey created by hand is now owned by its Intendant once the operator admits it, so it is deleted with its Intendant and kept or deleted by retention as the operator's own; before this fix it outlived its Intendant. A survey whose Intendant does not exist or is being deleted ends `Failed`, naming it. The operator gains `patch` on `TakeCareSurvey` in its namespace, to set that owner, decided by the product owner.
- The Ranger masks phone numbers with patterns of TakeCare's own, in place of agentgateway's `PhoneNumber` builtin, which took dates, timestamps and ids such as `INC-2024-0312` for phone numbers and missed national numbers. The patterns take international numbers (`+` or `00`), French and North American national numbers, and leave dates, ids, hashes, quantities, decimal values and times alone; a number written without separators is masked with the character before it. The phone mask is back on tool outputs, so a phone number a tool returns no longer reaches the provider, and the date of a folded alert in the Doc's grouped message is no longer masked. What the model reads in place of a number is now `<masked>`, not `<PHONE_NUMBER>`. Spec 09 §4 lists the forms missed and the runs taken by mistake; a customer who needs another national form adds it under `masking.patterns`. Decided by the product owner.
- The Ranger's gateway budget (`spec.caps.gateway`) now holds on the roles' routes that carry a per-model cap: a route-level rate limit replaces the gateway's in agentgateway, so before this fix those routes were bounded by their model cap alone. Each capped route's cap now repeats the gateway's budget, under the new Marker lines `gateway-budget` and `gateway-request-limit`, counted on that route alone: the gateway budget is shared by the routes without a model cap and repeated on each capped one, so it is not a ceiling on the gateway's total traffic. The Ranger also requires its policies to be `Attached` as well as `Accepted` before it reports them enforced.
- The Ranger's per-model Markers now cover the Intendant's model route: a cap on a model (`spec.caps.models`) caps the Intendant's route to it, and `spec.models` accepts `TakeCareIntendant`. Before this fix, the Intendant's model route had only the gateway-wide Markers: no per-model cap and no allowed-models refusal applied to it, even when set. A pass past its deadline, which kagent 0.10.6 cannot cancel, is bounded by that cap, and by the runtime's 500 model calls a run without one: set one.
- The site's Reference now lists `TakeCareIntendant` and `TakeCareSurvey`, missing since 0.3.0, and the site's build fails when the Reference's kinds and the CRDs differ.
- The Intendant no longer trusts the gateway's status alone for the argument rule on `get_rules`: agentgateway can report a policy Accepted and Attached while a field of it is dropped (for example under a Gateway-level traffic policy with `strategy.inheritance: Override`) or while the proxy keeps an older configuration. Each survey now sends one call the rule must refuse before it reads the alerting rules; if the gateway lets it through, or cannot be checked, the survey does not read them, its alerting layer says why, and `ConnectorsReady` names the problem.
- While a survey has found the gateway's argument rule on `get_rules` not enforced, the Intendant's metrics route no longer admits `get_rules` at all: its tool list is emptied, which a Gateway-level traffic policy cannot drop. Before this fix, the route still admitted `get_rules` by name to any caller the gateway admits, with any arguments. A later survey whose canary the rule refuses reopens it, and the survey after reads the rules again; the Intendant gets a `MetricsRouteClosed` and a `MetricsRouteReopened` event.
- The Intendant's import reads a cluster listing whose items all lack labels. Before this fix, a `resources_list` answer without the `Labels` key (the kubernetes MCP server's table printer can leave it out) was unrecognized, and the whole kind went to a `notSeen` line. Now its objects are read, and the service layer says in a `notSeen` line that no service was proposed from that listing's `app.kubernetes.io/part-of` or `app.kubernetes.io/name` labels. A listing where some items carry labels and others do not is still unrecognized, as is any other missing key.
- The Intendant reads the alerting rules item by item. Before this fix, a matcher value in a rule's expression holding the text `Duration:<n> Labels:` cut the expression there, and one holding `{Name:` made the whole answer unrecognized, which left the alerting layer with no rule. Now an expression runs to the first `Duration:<n> Labels:` outside PromQL's string literals. **Known limits remain**, because the pinned metrics server (mcp-prometheus v0.11.11) prints a rule's label and annotation values unquoted: someone who can already write alerting rules on that Prometheus can write, in an annotation, a whole rule that does not exist, and the import reads it as a rule (a name and an expression, nothing one of their real rules would not give; the rules after it are still read); and a label or annotation value holding `{Name:` without a whole rule still makes the answer unrecognized, a `notSeen` line on the alerting layer. Only a structured answer from the server can close them (spec 10 §4).
- The Intendant's import has a deadline of its own: half the pass timeout (5 minutes by default) from the moment the operator takes the survey up, and the inventory after the pass the same half. Before this fix, a slow or hung cluster or metrics server kept the import going call after call, each within its own timeout, eating the agent pass's time and leaving the survey `Running`. Past the deadline the survey fails with the reason "the import did not finish within half the pass timeout".
- The survey's inventory counts an agent given to another agent as a tool (kagent's tool type `Agent`) as one tool. Before this fix it counted none.

### Security

- No text of an engine task's status message reaches a record's reason any more. Before this fix, when a Doc's run ended in a state other than completed, the first line of the task's status message was written into the investigation's `status.reason` and into its Warning event, whatever `captureContent` said. That line can be a question the agent asked, the start of a model provider's error body (which can quote the conversation), or a tool server's error text. Now the reason holds the state, kagent's error code and the HTTP status only. The Ranger's refusal is still named, recognized by its exact sentence. A 429 is reported as a status, whoever sent it; the Ranger's `RequestsRateLimited` event says when it was the gateway's cap. Records already written keep their reason until retention removes them; they are the investigations whose `status.reason` starts with `EngineFailed: the task failed:` or `EngineFailed: the task stopped in state`, or `EngineFailedAfterAnswer:`, followed by text. Surveys were not affected: their agent pass records a fixed sentence.
- **Upgrade note, read before upgrading:** the `takecare` chart now refuses to render with an inline `kagent.database.postgres.url`, alone or beside `urlFile`. If you set one, before upgrading: 1. create a Secret in the engine namespace (`kagent` by default) with the key `url` holding the URL; 2. mount it under `kagent.controller.volumes` and `kagent.controller.volumeMounts`, for example at `/etc/kagent-db`; 3. set `kagent.database.postgres.urlFile=/etc/kagent-db/url` and empty `kagent.database.postgres.url`. Why: kagent 0.10.6 writes its configuration to its log at each start (`go/core/pkg/app/app.go`, line 394), the database URL with its credential included; an inline URL also sits in the controller's Deployment and in the release's values. The error names the steps and never prints the URL. The demo's bundled PostgreSQL sets no `url` and still renders; its password appears in the same log line, demo only.
- The operator's own Roles hold only the verbs its code calls: removed are `patch` on Docs, Intendants and demos (updated, for their finalizers); `get` and `update` on the statuses it patches, and `get` and `patch` on those it updates; `update` on every gateway and kagent object it writes by server-side apply; `get` on kinds it only lists and watches; `get`, `list`, `watch` and `update` on ConfigMaps in the engine namespace; every verb but `list` and `delete` on the retired `AgentgatewayModel`; and `update` on demos' finalizers. No behaviour changes; the demo's own Roles are unchanged. Its rights on ConfigMaps in the release namespace (`get`, `create`, `delete`, for the surveys' proposals) still cover every ConfigMap there, which Kubernetes cannot narrow: spec 10 §7 says so.
- **Upgrade note, read before upgrading:** the tools of a customer's MCP server declared by `url` are now `act` until the connector's `spec.tools` lists them as `read`. At the first discovery after the upgrade (within ten minutes), every tool of such a server that its own annotations called read-only becomes `act` and leaves the allow-list of every role below Expert, on the agent and at the gateway; the Doc and the Intendant then say that the connector has no read tool and why. Before upgrading, list each of those tools you trust in `spec.tools` with `class: read`; each listing is an override, recorded in `status.overrides` with a `ToolClassRelaxed` Warning, as before. After the upgrade, a `ToolClassChanged` Warning names each tool that changed, and `status.tools[].source` says `untrusted`. Why: the MCP specification says a client must consider tool annotations untrusted unless they come from a trusted server, and before this fix a customer's server that labelled a writing tool read-only had it given to Apprentice and Practitioner roles. The servers TakeCare ships (add-ons, a `cluster` connector's front) keep the annotation rule.
- A connector to a customer's own MCP server by `url` now reaches it through the gateway as the operator does. Before this fix, the gateway's backend carried neither the connector's `headersFrom` credentials nor TLS: an agent's call reached an `https` server in plain HTTP and without its credential, so it failed or, on an `http` server that does not check the credential, went through unauthenticated. The backend now names each header's Secret, and the gateway sends the value; it never appears in the backend, the connector's status or an event. An `https` URL gets TLS to its host, trusting the chart's `global.caBundle` (now also given to the gateway for these servers) or the system's roots. **Upgrade note:** `headersFrom` now takes at most eight entries, with names of the HTTP header form (the gateway's limits). A connector already stored beyond them stays stored, the API refuses a `headersFrom` beyond them from now on, and the connector gets no gateway backend (`BackendAccepted=False`, reason `HeadersUnsupported`) rather than a backend with part of its credentials. A server's certificate must be a leaf signed by a CA the gateway trusts: a self-signed certificate used as the server's own is refused.
- The MCP servers TakeCare ships (the Map, the corpus and the Slack report servers) refuse a request a browser sends across origins, with a 403: an `Origin` header naming another host, or `Sec-Fetch-Site: cross-site`. The MCP specification requires a Streamable HTTP server to check the `Origin` header, so that a web page cannot drive a server it can reach. The operator and the agents send no `Origin` and are unaffected.
- The Ranger's guards now scan what a tool returns. Before this fix, on agentgateway 1.6, a tool's output (a log line, a manifest, an environment value) reached the model provider unmasked and unfiltered: the guards read the system prompt and the messages only. Now card numbers, emails, social security numbers and phone numbers are masked in tool outputs too (phone numbers by TakeCare's own patterns, see Fixed); the shipped secret shapes (private keys, cloud access keys, common API tokens) are masked whole there and the run goes on; a shape that cannot be masked whole (a private key cut before its END line) refuses the model call. Every guard now names what it scans, so agentgateway 1.7's change of default does not change it. Still not scanned: a tool call's arguments, what the Expert's webhook guard would see in tool calls, and streamed answers. Upgrade note: a customer's own filtering patterns now also refuse a model call when they match a tool's output, and the Ranger's `RequestsMasked` events (now `Normal`, see Changed) fire more often.
- The chart's Gateway listener lets routes attach from the release namespace only (`allowedRoutes.namespaces.from: Same`); before this fix, an HTTPRoute in any namespace could attach to it and be served through the gateway. On upgrade, routes attached from other namespaces detach (their status says `NotAllowedByListeners`); every route TakeCare renders lives in the release namespace and stays.
- The operator's MCP client no longer follows redirects: the endpoint's headers, a Secret's included, were added on every request, so a followed redirect carried them to the redirect's target. A redirect now fails the call with its status.
- Before this fix, a caller able to reach the `kubernetes` connector's route through the gateway, and holding a Kubernetes token, could have the kubernetes MCP server act with that token instead of the add-on's read-only account, by sending it in the `Authorization` or `kubernetes-authorization` header; through the cluster chart's mTLS front, the `kubernetes-authorization` header passed the same way. Both charts now set the server's `cluster_auth_mode = "kubeconfig"`, so it always uses its own account; the server also refuses Secrets itself (`denied_resources`), and the front strips both headers. On upgrade, the server no longer offers `nodes_log`, `nodes_stats_summary`, `nodes_top` and `projects_list`, which our read-only RBAC never let succeed: they leave the connector's `status.tools` at its next discovery, `nodes_log` leaves the add-on's default content tools, and a Doc whose `spec.contentTools` still lists `nodes_log` gets a `ContentToolUnknown` Warning.

On the benches of 2026-11-13 (`google/gemini-3.7-flash`), the Doc scores 5 out of 5 (`test/bench/report-2026-11-13T1529Z.json`) and the Intendant 5 runs ok out of 5 (`test/bench/intendant-report-2026-11-13T1535Z.json`).

### Added

- The Intendant (spec 10), the role that keeps the Map with your teams.
  - **The kinds:** `TakeCareIntendant` and `TakeCareSurvey`.
  - **The controller:** each Intendant gets its conditions, an optional cron schedule, and its routes on the gateway: the Map's `map_at`, the cluster's read tools, and `get_rules`. `get_rules`' arguments are checked twice, by the gateway (a route-level rule on the metrics route) and by the operator.
  - **Survey triggers:** the schedule, a new Map revision, a registration (a bound connector or an engine agent appearing or changing; the Intendant's own agent does not count), and a survey created by hand. Triggers are debounced, and one pending trigger is kept in status.
  - **The survey:** one at a time per Intendant. It reads the Map at one revision, then imports the cluster's objects and Prometheus's alerting rules into proposals (add, update, remove), layer by layer. It also says what it could not read and which parts of the scope are blind spots.
  - **The agent pass:** after the import, the Intendant's kagent agent reads the cluster and the knowledge connectors and proposes dependencies, owners and runbooks, each with its evidence. Its answer is read strictly: only Map keys, knowledge sources and tool names pass. A pass that does not run, does not finish, or answers what cannot be read leaves the import's proposals and says why. Its usage is measured on its own model route.
  - **The inventory:** each survey lists, in `status.inventory` and an `inventory` layer, the agents and connectors in circulation on the cluster: the engine namespace's kagent Agents with the tools they are given, and the TakeCareConnectors with their discovered tools. The kagent Agents in the Intendant's scope are listed through the kubernetes connector, only when its add-on has the opt-in read rule `{group: kagent.dev, resource: agents}` in `addons.kubernetes.extraResources` (off by default). There are counts for all of them, and items for the first 100. No agent registry is installed (ADR 0019).
  - **Where the results go:** the first 20 proposals are in the survey's status, and the full set is in a ConfigMap owned by the survey. Each survey is one trace, and the gauges `takecare_survey_proposals` and `takecare_survey_not_seen` hold what awaits review. An ended survey is deleted after seven days; each Intendant keeps its newest.
  - **The digest:** at the Practitioner level, a survey whose proposals changed since the Intendant's last digest is posted to its report destination, through its report connector as the Doc's diagnoses are. The digest gives the counts, the first 20 keys, the survey and its Map revision, never an entry or its evidence. The outcome is in the survey's `status.published`, and the last digest posted is in the Intendant's `status.lastDigest`. The platform's `role-without-report` gap now counts an Intendant at Practitioner without a report connector.
  - **Operator rights**, in its own namespace:
    - get, list, watch, update and patch on `takecareintendants` and their status, and update on their finalizers;
    - create, get, list, watch and delete on `takecaresurveys`, and get, update and patch on their status;
    - create, get and delete on ConfigMaps, with no list, watch or update.
  - **The demo** runs an Intendant over its scenery and posts its digests to the review destination.
- The Map accepts a `knowledge` source on runbook entries, naming the record of a knowledge connector, and an alert's expression on `alertedBy` (spec 08).
- A how-to for reviewing the Intendant's proposals by hand and turning them into a Map pull request: `docs/how-to/review-proposals.md`.
- The Intendant bench, `make demo-bench-intendant N=5`: N surveys of the demo with a real model, each agent pass scored against a hand-written expected set. Its report gives per run the recall, the precision, what the merge dropped and why, the forbidden proposals and the usage, with keys and counts only. A release needs five runs ok out of five.

### Changed

- A role's model usage is measured on its own model route: the Doc's usage no longer counts another role's calls, such as an Intendant's agent pass, and `approximate` now means two runs of the same Doc overlapping (spec 02 §5).
- The demo needs 5 GB of Docker memory, up from 4 GB: with the Intendant's agent pass, the stack uses about 3.5 GiB idle and 4.1 GiB in an incident (ADR 0017 §6).
- The product site describes 0.3.0: the Intendant, the Base camp on the customer's Git (ADR 0019), and the Talkie and the Rope to come.
- The A2A client library is a2a-go 2.8.0.

### Fixed

- A retried investigation records its attempts exactly. The worker read the record from the cache before patching its status, and a copy that had not caught up with its own last write made the retry's increment undo it (`attempts: 1` on a run that took two). The worker now reads the record outside the cache and patches it with its resourceVersion, applying the change again on a conflict.
- `NOTICE` no longer depends on a network probe and carries no links: each package is listed with its name, version and license type, and the full texts ship in the release images. The links came from a probe of GitHub whose failures silently changed them from one run to the next, and three of them were dead (`github.com/blang/semver/v4`, `github.com/evanphx/json-patch/v5`, `gomodules.xyz/jsonpatch/v2`).

- The retention of investigations (spec 02): once an hour, the leader deletes the ended investigations (`Completed`, `Failed`, `TimedOut`, `Dropped`) older than the chart value `investigations.retention` (default `168h`), by their completion time, or their creation for a dropped one. - The Doc's publication (spec 02 §4, PR 4c-2a). A completed investigation is published through the Doc's report connector, by the operator, to the destination of the level it was created at: `trial` to `spec.report.trial` or status only, never `on-call`; `service` and `seasoned` to `spec.report.service`; a silent investigation nowhere. The message (Block Kit for Slack, the same as text for the log adapter) carries the header, the diagnosis unchanged, the time since the alert, the trace ID, the trial banner, the connectors the run went without, and the alerts of the incident folded in after the run started; with its usage. Three retries with backoff; the outcome in `status.published`, a final failure as a warning event. `takecare_investigation_duration_seconds` measures alert accepted to diagnosis published. The platform reports the production gap `role-without-report`: a role at the service level without a report connector.
- The usage and cost of an investigation (spec 02 §5, PR 4c-2b): the gateway's metrics read in Prometheus when the run starts and one scrape interval after it ends (chart value `operator.usageScrapeWait`, default 30 s), the difference priced with the model's pricing, `approximate` when the Doc may run investigations at the same time. The diagnosis is published once, with its usage. When the usage cannot be measured (Prometheus unreachable, a counter reset, a run resumed after a restart), the condition `UsageAttributed=False` says why and the message says "usage unknown", never a number.
- The Doc's runs (spec 02 §2, PR 4c-1): a worker on the leader takes the queued investigations, at most the Doc's `maxConcurrent` at once, and only for a Doc that is not suspended, `Ready` and `EngineReady` (a record otherwise waits `Queued`). It records `Running`, the start, the attempt, the engine, the trace ID and the connectors the run goes without (`status.degraded`), then the task ID before following the task. A lost task is started again once within the record's timeout; a new leader follows the runs left `Running` by their task ID. Ends: `Completed` with the diagnosis, `Failed` (`EngineFailed`, `EngineFailedAfterAnswer` with its text kept and never published, `TaskLost`, `StartFailed`, `DocMissing`) or `TimedOut` with the cancellation's result, each with a warning event; nothing is published yet. Every run is one trace: the root span `invoke_agent doc` from the alert's acceptance, with the GenAI and `takecare.*` attributes, the degradation, the outcome and the events `alert.accepted`, `investigation.started`, `investigation.retried`, `investigation.completed`.
- The run half of the engine boundary (spec 02 §2, ADR 0009): `engine.Runs` (start, poll, cancel) implemented for kagent 0.10.3 over A2A with a2a-go v2.6.0. The run goes through the gateway's A2A route, built from the agent's endpoint and never read from its card; it is sent non-blocking, and its task ID is recorded before it is followed (a task whose ID cannot be recorded is canceled). A cut read is retried; only a task the engine no longer knows is lost. At 90 % of the timeout the task is canceled: kagent 0.10.3's python runtime refuses, which is counted. A failure after an answer (`EngineFailedAfterAnswer`) is told apart and counted. Metrics `takecare_runs_total{role,outcome}`, `takecare_run_cancels_total{role,result}`. The Doc's message template (`internal/doc/message.tmpl`), golden-tested.
- The Doc's rendering (spec 02 §2): the `TakeCareDoc` controller checks its connectors, model and level, renders on the gateway one MCP route and one tool policy per connector (read tools only, from the connectors' discovered tools) and the A2A route to its agent, limited to the agent's own path, and renders in kagent the `Agent` (runtime `python`, content-capture switches per Agent, instructions in a ConfigMap) and one `RemoteMCPServer` per connector. A tool reference is never rendered without its allow-list: on kagent 0.10.3 an empty `toolNames` gives every tool. A connector never discovered is not given to the agent; one known but unavailable is, and the Doc says so (`Degraded`). The gateway's policies follow the connectors at once; a re-rendering of the agent waits while an investigation is `Running`, at most until its timeout (`status.renderPendingSince`). `EngineReady` needs the agent card to answer through the gateway's A2A route, with a two-minute start grace. Conditions `MissingConnectorType`, `ScopeNotCovered`, `SingleDocOnly`, `NotImplemented` (seasoned behaves as service); a finalizer removes the engine's objects, and the chart's README says how to finish a deletion without the operator.

### Changed

- The operator's image is renamed `takecare-agents-operator` (was `takecare-operator`), following the `takecare-agents-<component>` naming of the images (issue #22). A mirror of the images must add the new name. The Deployment, its ServiceAccount, the RBAC objects, the server-side apply field owner and the leader election ID keep their names, so an upgrade replaces the pods without a second leader or a field ownership conflict.

### Fixed

- The Doc was told it could read only the namespaces its alerts come from, and that every other namespace was denied, so it never reached a dependency living in another namespace its cluster connector reads (the demo's `DBProxy` in `ack-system`): its instructions now name every namespace the bound cluster connectors read. On the demo bench with the default model, 2 correct diagnoses out of 5 before, 5 out of 5 after.
- An investigation's usage is no longer doubled when Prometheus scrapes the gateway twice (a PodMonitor and an annotation job, or the demo's own job and the chart's kubernetes-pods job): the series are collapsed to their scrape target and the gateway's own labels before they are summed. The demo profile scrapes the gateway once.
- The Slack report server retries an inconclusive `auth.test` (no answer, a 5xx) every 10 seconds until the token has had a verdict, instead of waiting for the next 30-minute check. A network not ready when the pod starts no longer keeps the report connector not ready for half an hour.
